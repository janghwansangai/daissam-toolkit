### 윈도우 도우미(읽기만 했다)
`NativeHost.Send` 가 닫힌 통로에서 `IOException` 을 던질 수 있으나 부르는 곳(`Handle`·`Poll`·`PollRecorder`)이 모두 `try` 안이라 **알려진 충돌은 없다**. 전역 예외 처리기가 없어 처리되지 않은 예외에는 기본 대화상자가 뜬다 — `docs/ai/WINDOWS_HANDOFF.md` 에 방어 요청을 남겼다(소유 규칙상 직접 고치지 않았다).

### 알려진 한계 (고치지 않음 — 솔직하게)
- **녹화는 끝날 때까지 메모리(Blob)에 쌓는다**(1080p 약 2.2GB/시간). 녹화 창이 죽거나 컴퓨터가 꺼지면 그때까지 찍은 것이 모두 사라진다. 긴 수업은 ‘자동으로 멈추기’ 로 나눠 찍기를 권한다.
- 잠금 화면이 화면 전체를 덮어 휠의 목적지가 잠금 화면 자신이라, 잠긴 동안에도 뒤의 페이지가 휠로 스크롤될 수 있다(보이지 않는다). SVG·XML 문서 위에는 잠금 화면이 안 그려질 수 있다.
- 크롬 동기화 한도(약 96KB)를 넘으면(메모 100개 안팎) 나머지는 이 컴퓨터에만 남고 1분마다 다시 시도한다.
- 실제 화면 녹화·카메라·권한 대화상자·윈도우 실기기·인텔 맥은 이 시험으로 확인하지 못했다.

### 시험하며 배운 것
- **시험 장치가 만든 가짜 위반을 먼저 의심하라.** 처음 ‘내용이 확인받은 것과 다르다’ 가 계속 나왔는데, 사이드바 입력이 같은 메모를 덮어쓰는 ‘두 번째 글쓴이’ 였다. 같은 씨앗으로 원인을 걷어 내자 사라졌다.
- **시험 장치는 음성 대조로 살아 있음을 보여라.** 메모를 저장하지 않게 망가뜨린 복사본에서는 ‘메모가 사라졌다’, 옛 알람 복사본에서는 ‘알람이 남았다’ 가 정확히 나왔다.
- **가장 오래된 지원 버전에서 돌려 보라.** 최신 Chrome 에서는 한 번도 안 보이던 결함 2를 127 이 단번에 보여 줬다.
- **실제 사용 기록(충돌 보고서)이 가장 값진 증거다.** 4번 죽은 것을 사용자는 말하지 않았다.

## v0.39.2 — 측정으로 찾은 낭비 세 가지 고침

사용자 질문("컴퓨터가 느려지는가·최적화는?")에 맥에서 실제 측정으로 답하다 낭비 세 가지를 찾았고, "낭비만 고쳐줘" 요청으로 고쳤다. 측정 환경: Apple M4 Pro 24GB, Chrome for Testing 153(headless), 서로 다른 사이트 20개 탭, 메모리는 macOS `footprint`(활동 상태 보기의 ‘메모리’와 같은 실제 물리 사용량). 윈도우는 측정하지 못했다.

| 낭비 | 원인 | 고침 |
|---|---|---|
| ① 서비스 워커가 쉴 새 없이 깨어남 | `initialize()` 가 보낼 메모가 없어도 `flush-notes` 1분 알람을 늘 만들었다 | `settleFlushAlarm()` — 동기화를 기다리는 메모가 있을 때만 둔다. 시작할 때 보낼 것이 없으면 예전 버전이 남긴 알람도 지운다. 못 보낸 메모가 남으면 알람도 남아 1분마다 재시도 |
| ② 카메라·오디오 보조 프로세스 2개(약 48MB)가 늘 상주 | 사이드바가 시작할 때 `enumerateDevices()` 를 부르고 `devicechange` 를 들었다(캡처 화면과 유틸리티 녹음기 두 곳). **듣기만 해도** Chrome 이 `VideoCaptureService`·`AudioService` 를 띄운다(목록 읽기를 막아도 안 사라지고 듣기까지 막아야 사라짐을 확인) | `watchDevices()`/`pageShown()` — 그 화면이 열려 있는 동안만 읽고 듣는다(캡처 화면, 녹음기 칸을 펼쳤을 때). `saveRecord()` 는 목록을 채우기 전(`recDevicesListed`) 칸의 빈 값으로 저장해 골라 둔 장치를 지우지 않는다 |
| ③ 모든 페이지의 스크롤이 메인 스레드를 기다림 | `guard.js` 가 `wheel`·`touchstart` 를 ‘막을 수 있다’(`passive:false`)고 늘 들었다. 맥의 Command+휠 확대 듣는 쪽도 늘 있었다 | 휠·터치를 막는 듣는 쪽은 **잠겨 있을 때만**(`blockScrolling`). Command+휠 확대는 Command 를 누르는 동안만 막는 듣는 쪽을 두고(`armZoom`), 키 입력을 못 받은 프레임을 위해 막지 않는(passive) 감지를 하나 둔다 — 첫 눈금에서 알아채 배율을 바꾸고 다음 눈금부터 막는다 |

### 알려진 기존 동작(이번에 고치지 않음)
잠금 화면이 화면 전체를 덮고 있어 **휠의 목적지가 잠금 화면 자신**이다. 가드는 `composedPath().includes(host)` 로 잠금 화면 안의 입력을 통과시키므로(단추가 눌려야 하니까) 잠긴 동안에도 휠로 **뒤의 페이지가 스크롤될 수 있다**(눈에는 안 보인다). 시험을 처음 ‘잠기면 스크롤이 막힌다’ 로 썼다가 옛 코드에서도 같은 실패가 나서 알았다 — 이 보장은 처음부터 없었다.

### 시험하며 배운 것
- 새로 등록한 막는 듣는 쪽은 Chrome 이 알기까지 한두 프레임이 걸리고, 그 사이에 시작한 스크롤은 끝까지 이어진다(잠그는 순간의 문제일 뿐, 이어지는 입력은 막힌다).
- **시험이 실패하면 코드만 의심하지 말고 시험이 옛 코드에서도 실패하는지 먼저 볼 것.** 옛 코드에 같은 시험을 돌려 보니 시험의 가정이 틀린 것이었다.

### 미검증·한계
- 윈도우 측정 없음. 위 수치는 맥 한 대(headless)의 값이며 실제 Chrome(확장 여럿·탭 많음)에서의 체감은 다를 수 있다.
- 서비스 워커는 여전히 탭을 열거나 탭을 오갈 때(`guard.js` 의 `refresh()`) 깨어난다 — 사용자가 움직일 때 깨어나는 것이라 낭비로 보지 않았다.
- 카메라·오디오 보조 프로세스는 캡처 화면을 연 뒤에는 다시 뜬다(녹화를 하는 사람에게는 필요하다). 화면을 떠난 뒤 Chrome 이 얼마나 빨리 끄는지는 재지 않았다.

## v0.39.1 — 잠겨 있는 동안 화면이 깜박이며 원래 화면이 잠깐 보이던 것

사용자 보고: "핀으로 잠겨있을 때 한번 씩 화면이 깜박이면서 원래 화면이 잠깐 보이고 다시 잠기는 것 같았어."

**원인(두 겹, 측정으로 확인):**
1. `initialize()` 가 **서비스 워커가 켜질 때마다** 열린 모든 탭에 `guard.js` 를 다시 주입했다(`background.js`). guard.js 는 manifest 의 `content_scripts`(document_start, 모든 프레임)로 새 페이지에 이미 들어가므로 열려 있던 탭에는 확장이 켜진 뒤 한 번이면 된다. 그런데 서비스 워커는 30초 놀면 꺼지고, `flush-notes` 알람(1분)과 탭을 오가며 `refresh()` 가 보내는 메시지가 그때마다 다시 깨운다 → 잠금 중 **1분 안팎·탭 전환마다** 재주입.
2. `guard.js` 는 시작하자마자 **옛 잠금 화면을 지우고**(`dispose` + `[data-browser-sheriff-guard]` 삭제), 새 화면은 서비스 워커에 `state` 를 묻는 **비동기 왕복 뒤에야** 그렸다. 그 사이 원래 화면이 그대로 드러나고 입력도 막히지 않았다. 서비스 워커가 답하지 못하면 영영 지워진 채였다.

**측정(실제 Chrome 153, 잠근 뒤 서비스 워커를 껐다 깨움 / `executeScript` 로 직접 재주입, 앞 탭에 MutationObserver + rAF):**

| 탭 수 | 고치기 전 | 고친 뒤 |
|---|---|---|
| 6 | 깰 때마다 잠금 화면이 **한 번 사라짐, 8~9ms** | 0회 |
| 20 | 깰 때 13~15ms · 재주입 4~9ms, 프레임 노출 | 0회 · 노출 0 |
| 30 | 깰 때 17~18ms | 0회 |

탭이 많을수록 틈이 길어진다(재주입이 탭마다 이어진다). 위는 빠른 헤드리스 환경 수치이고, 사용자 컴퓨터(탭 많음·CPU 바쁨)에서는 더 길어 눈에 보였을 것이다 — **그 환경의 실제 틈은 재지 못했다.**

**고침:**
- `background.js`: 열린 탭 주입을 `chrome.storage.session.guardsInjected` 로 **확장이 켜진 뒤 한 번만**. storage.session 은 확장을 다시 불러오거나 업데이트·끔→켬·브라우저 재시작 때 비워진다 — 곧 다시 넣어야 하는 때와 같다.
- `guard.js`: 옛 화면은 **새 화면이 올라간 뒤에야**(`retire()`) 걷는다. 답을 기다리는 동안·답이 안 오는 동안에는 옛 화면을 그대로 둔다(안전한 쪽). 풀려 있다는 답이 오면 그때 걷는다. `dispose()` 도 옛 가드를 함께 걷어 입력 차단이 쌓이지 않는다.

**검사:**
| 검사 | 결과 |
|---|---|
| `npm test` | **119/119** (+5: guard 4 — 교체 순서·풀림 답·답 없음·겹침 / 주입 1회 1). 이 5개는 **옛 코드에서 실패**하고 고친 코드에서 통과함을 확인 |

| 갈아 낀 뒤 | 탭마다 잠금 화면 하나 · ‘PIN 확인하기’ 단추 동작 · 잠긴 동안 키 입력 차단 · 올바른 PIN 으로 해제되면 모든 탭에서 사라짐 · 해제된 탭의 키·클릭 정상 · 다시 잠그면 다시 생김 |

**미검증·한계:** ① `chrome.runtime.reload()` 는 이 시험용 브라우저(`--load-extension`, headless)에서 확장을 다시 살리지 못해(`ERR_BLOCKED_BY_CLIENT`) **실제 업데이트 경로는 돌려 보지 못했다** — 같은 일(열린 탭에 guard.js 직접 재주입)로 대신했고, 업데이트 뒤 옛 확장이 남긴 화면 정리는 기존 단위 시험(‘extension update removes stale DOM…’)이 맡는다. ② 페이지 스크립트가 잠금 화면 노드를 직접 지우는 경우는 다루지 않았다(관찰되지 않음).

**시험하며 배운 것:** 먼저 `chrome.runtime.reload()` 로 ‘다시 불러오기’ 를 쟀더니 0회가 나왔는데, 확장이 아예 사라져 있었다(옛 가드의 화면이 그냥 남은 것). **측정이 그럴듯해도 대상이 살아 있는지 먼저 확인할 것.**

## v0.36.5 — 찍는 동안 내 모습은 어느 방식이든 보이게

사용자 보고: “‘이 탭’ 으로 녹화는 되는데 찍는 동안 카메라 모니터 화면이 안 나온다.”
전에는 **화면 전체**를 담을 때만 앱이 동그란 카메라 창을 띄웠다(그때만 영상에 담기므로).

| 항목 | 방법 | 결과 |
|---|---|---|
| 고친 방향 | — | 두 가지를 나눴다 — **화면에 띄우는 것**(찍는 동안 내 모습: 어느 방식이든 띄운다)과 **영상 안에 합치는 것**(화면 전체를 담고 앱 창이 떠 있을 때만 합치지 않는다). 그래서 영상에는 언제나 카메라가 **딱 한 번** 담긴다 |

| 검사·포장 | — | `npm test` **81/81**, 맥 앱 0.36.5 서명·설치, 윈도우 exe 0.36.5 |
| **미검증** | — | 윈도우에서 앱과 Chrome 이 같은 카메라를 동시에 여는 것(SharedReadOnly 물러남) · 윈도우 전부 |

## 2026-09-19 v0.13.0 · 화면 조각 핀 (Snipaste 방식) (Claude)

Snipaste 를 조사해 붙이기(pin) 중심으로 옮겼다. 정리와 채택 범위는 PROJECT 의 '화면 조각 핀' 절에 있다.

### 실기기에서 확인한 것 (macOS, 실제 앱 실행)

- 클립보드가 비어 있을 때는 안내 알림만 뜨고 핀이 생기지 않는다(빈 클립보드로 보냈을 때 재현).

- **결함 2 수정 · 실행할 때마다 뜨던 모달 안내 창**: 안내 알림이 주 실행 루프를 잡고 있는 동안 사이드바에서 보낸 명령이 **하나도 전달되지 않는다**(알림을 띄운 채 `stop` 을 보내도 `state.json` 이 안 생김. 창 목록에서 층=8 모달 패널을 확인). 사이드바가 앱을 대신 켜는 경로에서 특히 나쁘다. 안내는 처음 한 번만 띄우고, 다음부터는 메뉴 막대에 ‘준비됨’ 을 잠깐 표시한다. 이전 버전부터 있던 결함이다.
- **결함 3 수정(예방)**: 조각을 내는 동안 30fps 포인터 타이머(macOS `updatePointer`) 와 16ms 타이머(Windows `UpdateView`) 가 숨겨 둔 발표 오버레이를 다음 틱에 도로 띄운다. 두 곳 모두 조각 중에는 빠져나가게 막았다.
- 분산 알림 처리를 주 스레드로 넘기도록 했다(`apply`). 실제로는 주 스레드로 오는 것을 확인했지만(진단값 `main:true`), 보장이 없는 API 라 방어로 남겼다.
- 고정 인증서 서명 복구: 마지막 빌드는 `stable certificate: Browser Sheriff Local Signing` 으로 서명되었고 `install.sh` 가 "권한이 그대로 유지됩니다" 로 넘어갔다.

## 2026-09-19 v0.18.0 · 집중 모드 단독 실행 · 막는 경고창 제거 · 핀 키 입력 수정 (Claude)

세 가지 신고가 한 뿌리에서 나왔다.

### 뿌리 1 — 모달 경고창이 앱 전체를 멈춘다

`showError` 는 `NSAlert.runModal()` 이다. **그 창이 떠 있는 동안 분산 알림(사이드바 명령)도 메뉴도 전혀 듣지 않는다.** v0.13.0 에서 실행 시 안내 창으로 이미 한 번 겪은 문제인데, "발표를 먼저 시작해 주세요" 같은 거절 경고가 같은 덫을 다시 놓고 있었다.

- 막지 않는 쪽지 창(`tell`, `NoticeView`)을 만들었다. 2.6초 뒤 스스로 사라지고 마우스를 받지 않는다.
- 명령으로 닿는 경고를 전부 쪽지로 바꿨다. 남은 모달은 **5개뿐이고 모두 ‘클립보드 도우미 등록/해제’ 메뉴** — 사용자가 그 자리에 있고 결과를 읽어야 하는 곳이다.
- 권한이 없을 때는 쪽지 + `openSettings` 로 허용할 자리를 바로 연다.

### 뿌리 2 — 집중 모드가 발표를 요구했다

`toggleFocus` 가 `guard active` 로 막고 모달을 띄웠다. 이제 **발표를 함께 켜고 이어서 집중 모드로 들어간다**(macOS·Windows 둘 다). 사이드바 스위치도 상태와 무관하게 늘 눌린다.

### 뿌리 3 — 핀 위의 낱개 키가 전부 죽어 있었다

`PinView.mouseDown` 이 곧장 `performDrag(with:)` 로 갔는데, **이 API 는 창을 키 창으로 만들지 않는다.** 그래서 핀을 눌러도 키보드가 그 핀으로 가지 않아 `t`(클릭 통과) · `c` · `s` · `1` · `2` · `3` · `0` · `Space` · `Esc` 가 **하나도 듣지 않았다.** 그리기·자르기만 되던 것은 그 둘만 `makeKeyAndOrderFront` 를 부르기 때문이다. 이제 누르는 순간 키 창으로 삼는다.

덧붙여 클릭 통과를 **바깥에서도 켜고 끌 수 있게** 했다(`pins-through`). 전에는 켜는 길이 핀 위에만 있고 끄는 길은 바깥에만 있어 어긋나 있었다.

### 확인한 것

- 실기기: `through` 가 `0 → 1 → 0` 으로 뒤집히고, 켠 핀이 없을 때 해제는 아무 것도 바꾸지 않는다. 명령을 연달아 보내도 앱이 계속 응답한다(모달 없음).
- 사이드바: 집중 모드 스위치가 `focus-on` 을 보내고 켜짐으로 바뀐다(발표 전에 눌러도). 클릭 통과 스위치가 `pins-through` 를 보내고 "2개 통과 중"을 표시하며 도크 단추도 함께 켜진다. **잠긴 버튼 0개.**
- 도크 9칸(`◌` 클릭 통과 추가).
- `npm test` 37/37, `npm run check` 통과. Swift 경고 0, .NET 오류 0 · 경고 0.

### 미검증

- 실제로 핀을 눌러 `t` 가 듣는지, 클릭이 정말 통과하는지. 외부에서 `NSWindow.windowNumber(at:)` 로 재려 했으나 **다른 앱 창은 보이지 않아 측정이 되지 않았다**(이 방법은 쓰지 말 것).
- 집중 모드 단독 실행의 실제 화면. 화면 기록 권한이 없어 실행하지 못했다.
- **서명 해결**: `codesign` 이 키체인 **SecurityAgent 승인 창(434×182)** 을 띄우는 것을 확인했다(`allow-signing-key.sh` 로는 이 ACL 이 풀리지 않는다). 사용자가 빌드 중 그 창에서 승인하자 곧바로 `stable certificate` 로 서명됐고, 배포 ZIP 도 그 빌드로 다시 만들었다. **앞으로 ad-hoc 으로 떨어지면 스크립트가 아니라 빌드 중 뜨는 그 창을 보라.**

## 2026-09-19 v0.19.0 · 권한 반복 요구 · 집중 모드 명령 · 도크 잘림 (Claude)

macOS 는 권한을 **그 앱의 서명**에 묶는다. `install.sh` 는 **임시 서명일 때만** 옛 기록을 지웠고, **임시 → 고정으로 넘어갈 때는 지우지 않았다.** 그래서 임시 서명 앱에 준 허용 기록이 고정 서명 뒤에도 남아 맞지 않는 상태로 버티고 있었다.

### 1. 집중 모드 토글이 안 움직이던 진짜 원인

앱 쪽은 v0.19.0 으로 이미 고쳐져 있었다(실기기 확인: `focus-on` → `presenting:true, focus:true`). 문제는 **사이드바가 너무 일찍 온 답을 믿는 것**이었다.
